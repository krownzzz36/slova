# ТЗ v2 — Онлайн-PvP «Слова — тебе на А»

**Область:** живая игра **двух (и более) игроков на разных телефонах** — реальное
время и асинхронный формат, матчмейкинг, комнаты, рейтинг, лидерборды, уведомления.
Здесь впервые появляется **бэкенд** и **серверная авторитетность** (иначе PvP не защитить
от читов).

> Локальная игра (один телефон, соло, бот, дневной пазл) — в `docs/ТЗ-Локальная-v1.md`.
> Стратегическое обоснование — в `docs/Геймдизайн-план-v1.md`.
> **Важно:** сначала стоит выпустить локальный скоринг (Задачи 1–4 локального ТЗ) — PvP
> опирается на ту же очковую экономику и модуль `src/score.js`.

---

## 0. Что принципиально меняется по сравнению с локальной версией

| | Локальная (v1) | PvP (v2) |
|---|---|---|
| Источник истины | клиент | **сервер** (authoritative) |
| Проверка слова | клиентский `Dict` | **сервер** (клиент — только для мгновенного UX-превью) |
| Часы/таймер | локальные | **серверные** (клиентским временам нельзя доверять) |
| Идентичность | нет | **Telegram `initData`** (HMAC-валидация) |
| Состояние партии | `Storage`/`resume` | **БД + комната (realtime)** |
| Сеть | офлайн | **онлайн**, с деградацией/реконнектом |

**Ключевой принцип: сервер решает всё, что влияет на исход.** Клиент показывает и
предсказывает, но не определяет валидность хода, время и счёт. Любой ход проверяется
на сервере; клиентский результат — оптимистичный, сервер подтверждает или откатывает.

## 1. Архитектура (решение и альтернативы)

**Огромное преимущество текущей кодовой базы:** чистые модули `rules.js`, `morph.js`,
`score.js` — это UMD без DOM и без зависимостей. Они **исполняются и в браузере, и в
Node/Workers**. Значит серверная проверка хода переиспользует **тот же самый код**, что
и клиент → гарантированный паритет правил. Словарь `data/dict-data.js` тоже грузится в
Node/Workers. Это резко удешевляет бэкенд: правила уже написаны и покрыты тестами.

**Рекомендуемый стек (primary): Cloudflare Workers + Durable Objects.**
- **Durable Object = одна партия.** Каждая живая партия — отдельный DO-инстанс:
  хранит авторитетное состояние (цепочка, чей ход, часы, `used`), принимает WebSocket от
  обоих игроков, рассылает обновления. Идеальная модель для пошаговой комнаты.
- **Workers** — REST (матчмейкинг, профиль, рейтинг, история), валидация `initData`,
  вебхук Telegram-бота для уведомлений.
- **Хранилище:** DO-storage — состояние живой партии; **D1 (SQLite)** — профили, рейтинг,
  завершённые партии, лидерборды; **KV** — очередь матчмейкинга/кеши.
- **Плюсы:** масштаб до нуля (платишь за использование), глобальная задержка, WS «из
  коробки», состояние партии живёт в одном месте без гонок. Дёшево на нашем объёме.

**Альтернатива (managed, меньше кода): Supabase.** Postgres + Realtime (broadcast/
presence) + Edge Functions. Быстрее стартовать, но авторитетную пошаговую логику придётся
делать в Edge Functions/RPC, а realtime-канал — не «комната с состоянием», а pub/sub —
больше ручной синхронизации против гонок.

**Альтернатива (полный контроль): Node (Fastify) + Socket.io + Redis + Postgres** на
Fly.io/Railway. Максимальная гибкость, но сам держишь сокет-сервер, презенс и масштаб.

**→ РЕШЕНИЕ (требует подтверждения владельцем):** Cloudflare Workers + Durable Objects
+ D1. Ниже ТЗ написано под неё, но модель данных/протокол переносимы.

## 2. Идентичность — Telegram `initData` (без паролей)

**Проблема.** PvP нужен устойчивый идентификатор игрока, но заводить аккаунты/пароли —
плохо (безопасность, трение). У Telegram Mini App это решено нативно.

**Что сделать.**
- Клиент шлёт `Telegram.WebApp.initData` в каждый защищённый запрос (заголовок/поле).
- Сервер **валидирует HMAC** `initData` секретом из токена бота (алгоритм Telegram:
  `secret = HMAC_SHA256(bot_token, "WebAppData")`, сверка `hash`), проверяет `auth_date`
  (не старше N часов). Только после этого доверяет `user.id`.
- `user.id` Telegram = первичный ключ игрока. Профиль (имя, аватар-буква, цвет, рейтинг)
  создаётся при первом входе.
- **Никаких паролей/секретов на клиенте.** Токен бота — только на сервере.

**Критерии приёмки.**
- [ ] Запрос с невалидным/просроченным `initData` отклоняется (401).
- [ ] `user.id` берётся только из проверенного `initData`, не из тела запроса.
- [ ] Профиль создаётся при первом входе; повторный вход находит существующий.

**Оценка:** S (валидация) + S (профиль).

## 3. Авторитетная модель партии (сердце PvP)

**Проблема.** Клиентскому словарю и таймеру доверять нельзя — их тривиально подменить.

**Что сделать.**
- Durable Object партии хранит: `players[]`, `turn`, `required` (нужная буква),
  `lastWord`, `used` (Set ключей), `usedRoots`, часы каждого игрока, `scores`, `log`, `status`.
- **Каждый ход валидируется на сервере** переиспользованием `Rules.checkMove` + серверный
  `Dict` (тот же `dict-data.js`) + `score.js`. Клиент шлёт только слово-кандидат и свой
  локальный тайминг **как подсказку**, но зачёт времени — по серверным часам.
- Результат хода сервер рассылает обоим: принято/отклонено, новое `required`, начисленные
  очки, обновлённые часы, чей ход.
- **Оптимистичный клиент:** локально показывает ход сразу (свой `Dict` для мгновенного
  «принято»), но помечает «ожидает подтверждения»; при расхождении с сервером — откат.
- Правила приёма (буква, словарь, повтор, форма, однокоренное, дефис, ё=е) — **идентичны**
  локальным, потому что это тот же модуль. Спорные ветки (`overridable`, «всё равно
  засчитать») в рейтинговом PvP **выключены** (нельзя вручную протаскивать слова).

**Критерии приёмки.**
- [ ] Ход принимается/отклоняется сервером; клиент не может протащить несловарное слово.
- [ ] Правила PvP совпадают с локальными (тот же `rules.js`/`score.js`), кроме ручного зачёта.
- [ ] Расхождение оптимистичного клиента с сервером корректно откатывается в UI.
- [ ] Повтор/тупик/смена буквы считаются на сервере одинаково для обоих.

**Оценка:** L.

## 4. Форматы матча (гейм-дизайн PvP)

Механика «цепочки» ложится в дуэль напрямую: игроки по очереди продолжают одну цепочку
на нужную букву, без повторов, на часах. Определяем два формата:

**A. Живая дуэль (realtime), рекомендованный дефолт.**
- Шахматные часы на игрока: базовое время (напр. 2:00) + инкремент (напр. +5 с/ход,
  Fischer). Кончилось время — поражение.
- Победа: (1) соперник не ответил в срок/пас на «сдачу» — по правилам; или (2) по
  очковой экономике (`score.js`) за фиксированное число ходов/времени. **Рекомендация:**
  гибрид — играем до истечения часов; при истечении сравниваем очки; при равенстве —
  тай-брейк (больше слов → длиннее суммарно → меньше среднее время хода).
- **Ловушки решают:** закончить на трудную букву (Задача 3 локального) даёт очки и
  давит на часы соперника. Это и есть стратегический слой дуэли.

**B. Асинхронная партия (Words-With-Friends style).**
- Ход в любое время; дедлайн на ход (напр. 24–72 ч). Пропуск дедлайна → форфейт хода
  или партии (настройка). Уведомление боту при передаче хода (раздел 8).
- Победа — по той же очковой экономике за N ходов на игрока (напр. 10) или до сдачи.

**Критерии приёмки.**
- [ ] Живая дуэль: серверные часы с инкрементом; истечение = поражение; тай-брейк однозначен.
- [ ] Асинхрон: дедлайн хода, форфейт при пропуске, продолжение из уведомления.
- [ ] Ловушка (трудная финальная буква) даёт очки и передаёт «неудобную» букву сопернику.
- [ ] Детский/казуальный вариант без рейтинга — мягче (больше времени, без форфейт-штрафа).

**Оценка:** M (дизайн + серверные часы) — опирается на модуль часов из раздела 3.

## 5. Матчмейкинг и комнаты

**Проблема.** Игроков надо свести — с другом и со случайным соперником.

**Что сделать.**
- **Игра с другом по коду/ссылке.** Создать комнату → короткий код + deep-link
  (`startapp=room_XXXX`). Друг открывает Mini App по ссылке → попадает в комнату. Это
  «повзрослевший» вызов-по-ссылке из локального ТЗ (Задача 7), но теперь с живым сервером.
- **Быстрый матч (quick match).** Очередь в KV: игрок встаёт в очередь с диапазоном
  рейтинга; сервер сводит двоих близких по MMR; при долгом ожидании расширяет диапазон;
  фолбэк — предложить бота (из локального ТЗ) как «пока ищем соперника».
- **Реванш** после партии (кнопка «ещё раз» тем же двоим).
- Настройки комнаты создателем: формат A/B, часы, рейтинговая/дружеская, словарные тиры
  (имена/города/любые части речи — как в `CFG`).

**Критерии приёмки.**
- [ ] Комната по коду/ссылке: второй игрок заходит и партия стартует.
- [ ] Быстрый матч сводит двоих; при таймауте предлагает бота, не зависает.
- [ ] Реванш и настройки формата работают; дружеские партии не влияют на рейтинг.

**Оценка:** L.

## 6. Realtime-протокол (WebSocket)

**Что сделать.** WS между клиентом и DO-комнатой. События (черновик):
- **Клиент → сервер:** `join{initData, roomId}`, `move{word, clientTs}`, `pass`,
  `swap`, `resign`, `ping`, `rematch`.
- **Сервер → клиент:** `state{players, turn, required, lastWord, clocks, scores, log}`
  (полный снапшот при join/reconnect), `moveResult{ok, reason, score, nextRequired,
  clocks, turn}`, `opponentMove{...}`, `clockTick{clocks}` (или клиент экстраполирует
  между `state`), `gameOver{result, ratingDelta}`, `error{code}`.
- **Синхронизация часов:** сервер — источник; клиент экстраполирует локально между
  снапшотами, корректируется на каждом `moveResult`/`state`. Никаких начислений времени
  по клиентским `Ts`.
- **Идемпотентность хода:** каждый `move` с `clientMoveId`; повтор при реконнекте не
  задваивает.

**Критерии приёмки.**
- [ ] Полный снапшот состояния приходит при входе/реконнекте; UI восстанавливается точно.
- [ ] Ходы соперника видны в реальном времени; часы согласованы у обоих (±сетевой лаг).
- [ ] Дубли `move` при переподключении не проходят дважды (идемпотентность).

**Оценка:** L.

## 7. Реконнект и краевые случаи

**Проблема.** Мобильная сеть рвётся; сворачивание Mini App; двойные вкладки.

**Что сделать.**
- **Grace-окно** при обрыве: сервер держит место N секунд (напр. 30), клиент
  переподключается и получает `state`. Часы на ходящем идут (в живой дуэли), у ждущего — нет.
- Превышение grace в живой дуэли → авто-поражение по дисконнекту (с рейтинг-штрафом,
  раздел 9) — иначе абуз через выход. В казуальной/асинхронной — мягко (пауза/форфейт хода).
- Одна активная сессия на игрока в партии (вторая вкладка вытесняет первую с предупреждением).
- Сворачивание Mini App (`visibilitychange`) не должно мгновенно ронять партию — используем
  grace-окно, а не мгновенный разрыв.

**Критерии приёмки.**
- [ ] Кратковременный обрыв (<grace) не рвёт партию; состояние и часы восстановлены.
- [ ] Долгий обрыв в рейтинговой дуэли = поражение по дисконнекту, зафиксировано честно.
- [ ] Вторая вкладка не создаёт «двойного игрока».

**Оценка:** M.

## 8. Асинхрон и уведомления через бота

**Проблема.** Async-партия бесполезна без напоминания «твой ход».

**Что сделать.**
- При передаче хода в async-партии сервер шлёт игроку сообщение через **Telegram Bot API**
  (`sendMessage`) с deep-link прямо в эту партию (`startapp=game_XXXX`).
- Напоминание о приближении дедлайна (напр. за 6 ч), финальное — при форфейте.
- Частота/тихие часы — ограничить, чтобы не спамить (антиспам, настройка «не беспокоить»).
- Открытие по deep-link ведёт сразу в нужную партию (парс `start_param` в `boot`).

**Критерии приёмки.**
- [ ] При передаче хода приходит уведомление с рабочим deep-link в конкретную партию.
- [ ] Напоминание о дедлайне и форфейт-уведомление приходят; спам ограничен; есть «не беспокоить».

**Оценка:** M.

## 9. Рейтинг, лидерборды, сезоны

**Проблема.** Без прогрессии соревновательность быстро выгорает.

**Что сделать.**
- **Рейтинг ELO** (или Glicko-2 для точности при редкой игре). K-фактор выше для новичков
  (провижн-партии), ниже дальше. Считается **на сервере** по итогу рейтинговой партии.
- **Штраф за дисконнект/сдачу** в рейтинге (раздел 7) — как поражение, чтобы не абузили.
- **Лидерборды:** глобальный, недельный (сброс), «друзья» (пересечение TG-контактов/
  сыгранных соперников). Хранение в D1, кеш в KV.
- **Сезоны** (месяц): софт-сброс рейтинга, сезонные награды — косметика (скины букв/темы,
  привязка к монетизации из локального ТЗ, Задача 11).
- Показ рейтинга/ранга в профиле и на экране матча.

**Критерии приёмки.**
- [ ] Рейтинг меняется по итогу рейтинговой партии; дружеские/казуальные не влияют.
- [ ] Дисконнект/сдача в рейтинге считается поражением.
- [ ] Лидерборды (глоб/неделя/друзья) корректны и быстры; сезон сбрасывается по расписанию.

**Оценка:** L.

## 10. Модель данных и API (черновик)

**Таблицы (D1):**
- `players(tg_id PK, name, color, created_at, rating, games, wins, season_rating)`
- `games(id PK, mode, ranked, player_a, player_b, winner, score_a, score_b, started_at,
  ended_at, end_reason, seed, chain_json)`
- `leaderboard_week(week, tg_id, points, PRIMARY KEY(week,tg_id))`
- `achievements(tg_id, key, unlocked_at)` — можно шарить с локальными достижениями.

**Живое состояние партии** — в DO-storage (не в D1): `{players, turn, required, lastWord,
used[], usedRoots, clocks, scores, log[], status, deadline}`.

**REST (Workers), все под валидацией `initData`:**
- `POST /me` — профиль (создать/получить). `GET /me/stats`.
- `POST /match/quick` — встать в очередь. `POST /match/cancel`.
- `POST /room` — создать комнату (настройки) → `{roomId, code}`. `POST /room/join {code}`.
- `GET /games/active` — активные async-партии игрока. `GET /game/:id` — снапшот.
- `GET /leaderboard?scope=global|week|friends`.
- `POST /telegram/webhook` — апдейты бота (для уведомлений/диплинков).

**WS:** `wss://…/room/:id` (см. раздел 6).

**Критерии приёмки.**
- [ ] Схема поддерживает realtime и async, рейтинг, лидерборды, историю; миграции версионированы.
- [ ] Все защищённые эндпоинты требуют валидный `initData`.

**Оценка:** M (схема+REST), плюс труд по разделам 3/6.

## 11. Античит и честность

**Проблема.** Любая клиентская проверка обходится; в рейтинге это критично.

**Что сделать.**
- **Сервер — единственный судья** слова, времени, повторов, очков (раздел 3). Клиентский
  `Dict` — только оптимистичное превью.
- **Паритет словаря:** сервер и клиент собираются из одного `build_dict.py`; версия
  словаря фиксируется в партии (`seed`/`dictVersion`), чтобы обе стороны судились одинаково.
- **Рейт-лимиты:** на ходы (анти-скрипт), на матчмейкинг, на создание комнат.
- **Тайминг только серверный;** клиентские `Ts` — подсказка, не начисление.
- **Ручной зачёт/«свои слова» выключены в рейтинге** (иначе протаскивание несловарных слов).
- Логировать подозрительное (ходы быстрее человеческого предела, аномальная точность) для ревью.

**Критерии приёмки.**
- [ ] Модифицированный клиент не может протащить несловарное слово/лишнее время/очки.
- [ ] Обе стороны судятся одной версией словаря; результат воспроизводим из `chain_json`.
- [ ] Рейт-лимиты срабатывают; ручной зачёт недоступен в рейтинге.

**Оценка:** M (поверх раздела 3).

## 12. Модерация и анти-абуз

**Проблема.** Живой PvP с чужими людьми = токсичность, абуз, неприличные имена.

**Что сделать.**
- **Имена:** фильтр по стоп-листу (переиспользовать корневой стоп-лист из `build_dict.py`);
  дефолт — имя из Telegram; запрет ссылок/оскорблений.
- **Rage-quit / намеренный слив времени:** штраф рейтинга за дисконнект (раздел 7),
  анти-«таймер-стеллинг» (систематическое досиживание до последней секунды — мягкий флаг).
- **Жалоба/блокировка:** `report`/`block` соперника; заблокированный не попадёт в матчмейкинг.
- **Никакого свободного чата** в MVP (только предустановленные эмодзи-реакции) — снимает
  целый класс модерации. Живая семейная игра остаётся на локальном pass-and-play.

**Критерии приёмки.**
- [ ] Неприличное имя не проходит; есть дефолт из Telegram.
- [ ] Report/block работают; заблокированный не сводится в быстрый матч.
- [ ] Нет свободного текстового чата в MVP (только реакции).

**Оценка:** M.

## 13. Клиент: что добавляется

**Что сделать.**
- Экран лобби: «Быстрый матч» / «Играть с другом (код/ссылка)» / «Мои партии (async)» /

- Экраны профиля, лидерборда, истории рейтинговых партий.
- Деградация без сети: понятное «нет соединения», авто-реконнект, не терять введённое слово.

**Критерии приёмки.**

## 14. Инфраструктура, масштаб, наблюдаемость

- **Окружения:** dev/prod; секреты (токен бота) — в secrets Workers, не в репозитории.
- **Стоимость:** Workers/DO/D1 масштабируются до нуля — на старте ≈ бесплатно, растёт с DAU.
- **Наблюдаемость:** логи ходов/ошибок, метрики (матчей/день, среднее время матча, %
  дисконнектов, длина очереди матчмейкинга), алерты на рост ошибок.
- **Версионирование словаря/правил** в партии — чтобы деплой новой версии не «переосудил»
  идущие партии.
- **Тесты:** серверная валидация хода покрыта юнитами (тот же `rules.test.js`-подход);
  интеграционный тест «партия от join до gameOver»; нагрузочный на матчмейкинг.

**Критерии приёмки.**
- [ ] Секреты не в репозитории; dev/prod разделены.
- [ ] Есть базовые метрики и алерты; серверная логика покрыта тестами.
- [ ] Деплой новой версии не ломает идущие партии.

**Оценка:** M.

## 15. Дорожная карта PvP (по фазам)

| Фаза | Что | Результат |
|---|---|---|
| **PvP-0** | Бэкенд-скелет: Workers+DO+D1, валидация `initData`, профиль (2, 3, 10) | Игрок опознаётся, есть профиль |
| **PvP-1** | Авторитетная партия + WS + живая дуэль с другом по ссылке (3, 4A, 5-друг, 6, 7) | Двое играют живую дуэль по ссылке |
| **PvP-2** | Быстрый матч + рейтинг ELO + реконнект (5-quick, 9, 7-раздел) | Случайный соперник + рейтинг |
| **PvP-3** | Async-партии + уведомления бота (4B, 8) | Игра «на ходу», как WWF |
| **PvP-4** | Лидерборды, сезоны, модерация, античит-полировка (9, 11, 12) | Соревновательный контур |

**Рекомендация:** PvP-0 → PvP-1 (живая дуэль с другом — самый дешёвый способ проверить
спрос) → дальше по данным. Не строить матчмейкинг/рейтинг, пока «дуэль с другом» не
показала, что в PvP играют.

## 16. Риски и снятие

- **Спрос на PvP не подтверждён.** → Сначала локальный «вызов по ссылке» (локальное ТЗ,
  Задача 7) и «дуэль с другом» (PvP-1) как дешёвый тест; матчмейкинг/рейтинг — только после.
- **Читы.** → Сервер-авторитет + паритет словаря + серверные часы (разделы 3, 11).
- **Токсичность.** → Нет свободного чата в MVP, только реакции; report/block (раздел 12).
- **Мобильная сеть рвётся.** → Grace-окно + реконнект + идемпотентные ходы (разделы 6, 7).
- **Сложность/стоимость поддержки.** → Serverless до нуля; переиспользование чистых
  модулей правил; async-формат снижает требования к realtime.
- **Расхождение правил клиент/сервер.** → Один и тот же `rules.js`/`score.js` на обеих
  сторонах; версия правил фиксируется в партии.

- [ ] `initData` валидируется; профиль создаётся/находится.

- [ ] Секреты вне репозитория; метрики/алерты; серверные тесты зелёные; версия правил в партии.
- [ ] Оптимистичный клиент и откат незаметны на хорошей сети; потеря сети показывается понятно.
